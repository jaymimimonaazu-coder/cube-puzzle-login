# NEON LATTICE — 本番想定サーバー版

`neon/` のブラウザ完結デモを、**サーバー側照合**の構成に作り直したものです。

> **監査済み**: 2系統の独立監査（Claude攻撃者エージェント / Codex）を実施し、
> 指摘13件（高3・中6・低4）をすべて修正しました。詳細は
> [`../AUDIT_FINDINGS.md`](../AUDIT_FINDINGS.md)、原文は
> [`../CODEX_REVIEW.md`](../CODEX_REVIEW.md) を参照してください。

## 何が変わったか

| | ブラウザ完結版 (`neon/`) | サーバー版 (これ) |
|---|---|---|
| 照合の場所 | ブラウザ内 | **サーバーのみ** |
| 保存形式 | localStorage に SHA-256 | **Argon2id**（ソルト自動付与）でDB保存 |
| レート制限 | メモリ（リロードで消える） | **DB管理＋原子的消費**（並行リクエストでも回避不可） |
| 弱い配置 | 制限なし | **登録時に拒否**（規則検査。bit値は保証しない） |
| 上書き・削除 | 誰でも可能 | **セッション必須** |
| クライアントが持つ秘密 | ハッシュ | **なし**（毎回サーバーへ問い合わせ） |

## 構成

```
server/
├── app/
│   ├── main.py       # FastAPI・認可・DoS対策
│   ├── passcode.py   # 正規化・形式検証・規則検査
│   └── store.py      # Argon2id + 原子的レート制限 + セッション
├── static/
│   └── index.html    # ネオン立方体UI（サーバーAPIと通信）
├── tests/            # pytest 50件（監査項目の回帰テスト含む）
└── requirements.txt
```

## セットアップと起動

```bash
cd server
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# 開発起動（DBはメモリ。永続化するなら NEON_DB_PATH を指定）
NEON_DB_PATH=neon.db uvicorn app.main:app --reload --port 8000
```

ブラウザで `http://localhost:8000` を開きます。
画面下の「切替」ボタンで ENROLL（登録）と AUTHENTICATE（認証）を選びます
（サーバーに「そのユーザーは登録済みか」を問い合わせる方式は、
ユーザー列挙につながるため廃止しました）。

## API

| メソッド | パス | 認証 | 内容 |
|---|---|---|---|
| POST | `/api/enroll` | 不要 | 新規登録のみ。既存名は 409、弱い配置は 422、過大な本文は 413 |
| POST | `/api/reenroll` | **必要** | 本人のパスコード変更。旧セッションは失効 |
| POST | `/api/authenticate` | 不要 | 照合。成功で 200＋session、失敗 401、混雑 503 |
| POST | `/api/forget` | **必要** | 本人の登録削除 |
| POST | `/api/logout` | **必要** | セッション失効 |
| GET | `/api/me` | **必要** | セッションの持ち主 |

認証が必要なものは `Authorization: Bearer <session>` を付けます。
`/api/status/{username}` は**廃止しました**（登録済みユーザーを誰にでも公開していたため）。

`passcode` は `[[c,c],[c,c],[c,c],[c,c],[c,c],[c,c]]`（6面×2セル、各 0〜15）。
面内・面をまたぐ入力順は問いません（サーバーで正規化）。

## セキュリティ設計

| 対策 | 実装 |
|---|---|
| **オフライン耐性** | Argon2id（time_cost=3 / 64MiB / parallelism=2） |
| **ソルト** | Argon2 が利用者ごとに自動付与。レインボーテーブル無効 |
| **レート制限** | **検証の前に試行枠を原子的に消費**。`BEGIN IMMEDIATE` + 相対UPDATE で並行リクエストでも回避不可（監査H-1） |
| **IP制限** | 30回/5分。他人を狙ったロックアウトDoSを緩和（監査M-6） |
| **認可** | 変更(`/api/reenroll`)・削除(`/api/forget`)はセッション必須。`enroll` は新規のみ（監査H-2） |
| **セッション** | DB保存・トークンはハッシュ化・1時間期限・失効可能。資格情報変更で全失効 |
| **弱い配置の拒否** | `find_weak_patterns()` による規則検査（監査H-3） |
| **ユーザー列挙対策** | `/api/status` を廃止。未登録・誤り・ロック中で応答と計算時間を揃える |
| **DoS対策** | 本文4KB上限（解析前に413）、Argon2同時実行4件まで（飽和時503） |

### 強度判定について（重要な設計変更）

当初は `estimate_bits()` が「推定41.4bit」のような値を返していましたが、**廃止しました**。

監査で指摘されたとおり、**単一の完成済みパスコードから、その利用者が用いた確率分布やエントロピーを推定することはできません**。
実際、旧実装は3種を繰り返す配置（実効9.5bit）を「30.44bit」と判定して通していました。

現在は `find_weak_patterns()` が**既知の弱い規則に当てはまるかだけ**を判定します。
これは強度の保証ではなく、明らかな悪手を弾くフィルタです。
理論値41.44bitを実際に主張できるのは `passcode.generate_random()`（サーバー側CSPRNG生成）を使う経路のみです。

### 攻撃の再現（いずれも防御を実測で確認）

`neon/` 版を破った攻撃と、監査で見つかった脆弱性を修正後の実装に当てた結果:

```
[攻撃A] localStorage を読む      → 盗めるものが無い（鍵はサーバーDBのArgon2idのみ）
[攻撃B] ハッシュのすり替え        → 401（判定はサーバー）
[攻撃C] リロードで制限リセット    → 効かない（DB管理）
[H-1] 並行30本でレート制限回避   → 検証到達5回・ロック25件（監査前は30本すべて通過）
[H-2] 無認証でアカウント上書き   → 409 / 無認証削除 → 401（監査前はどちらも成功）
[H-3] 弱い配置の登録             → 422で理由付き拒否（監査前は通過）
[M-5] /api/status でユーザー列挙 → 404（廃止済み）
[M-1] 200万要素の入力によるDoS   → 解析前に413（監査前は6.6秒消費）
```

## 本番導入で追加すべきこと

このリポジトリは「サーバー照合＋ストレッチ＋レート制限＋強度チェック」までを示す実装です。
実運用ではさらに以下が必要です。

- **TLS必須**。パスコード（配置）を平文で送るため、HTTPSでなければ盗聴される
- **セッションを Redis 等へ**（現在はSQLite。単一ノード想定）
- **レート制限をリバースプロキシ側でも多層化**（分散攻撃への備え）
- **監査ログ**（失敗の集中を検知）
- 色覚特性への配慮（面の識別を色だけに依存させない）
- 高い保証が必要なら **WebAuthn 等と併用**し、MFAの1要素として使う

### 設定できる環境変数

| 変数 | 既定 | 内容 |
|---|---|---|
| `NEON_DB_PATH` | `:memory:` | SQLiteのパス。永続化するなら `neon.db` など |
| `NEON_CORS_ORIGINS` | 空（同一オリジンのみ） | カンマ区切りの許可オリジン |
| `NEON_REVEAL_LOCK` | 未設定（秘匿） | `1` にするとロック状態を429+retry_afterで返す（デモ用）。既定では列挙対策のため秘匿 |

## 位置づけ（率直に）

レート制限が正しく機能する前提で、**オンライン総当たりは事実上不可能**です
（全探索に最悪1700万年・平均850万年）。ただしこれは監査で見つかった競合バグを
修正して初めて成り立つ数字でした。

DB漏洩時のオフライン耐性は Argon2id で大きく上がりますが、**無限ではありません**。
1GPUで約47年、大規模なGPU群（1000台規模）なら約17日という試算です
（Argon2idの2,000 H/s は**未実証の仮定**であり、実測なしに一般化はできません）。

また 41.44bit は**一様ランダムに選んだ場合の理論値**です。利用者が自分で選ぶ場合の
実効エントロピーはこれより低くなります。

したがって、**単独の認証手段ではなく MFA の1要素**として使うのが最も堅実です。
