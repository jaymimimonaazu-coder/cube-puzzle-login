# NEON LATTICE Cube Passcode Auth セキュリティレビュー

## 結論

現状の実装には、本番公開前に修正すべき問題があります。特に重要なのは次の3点です。

1. `/api/forget` が未認証で、第三者が任意ユーザーの資格情報を削除できる
2. 認証失敗回数の更新がアトミックではなく、並列リクエストでレート制限を回避できる
3. `estimate_bits()` はエントロピー推定として成立せず、実質的に弱いパスコードを許可する

---

## セキュリティ上の指摘

### 1. 未認証で資格情報を削除できる

- **深刻度**: 高
- **成立性**: 実際に再現可能
- **該当**: `server/app/main.py` — `forget()`

```python
@app.post("/api/forget")
def forget(body: PasscodeBody):
    store.forget(body.username)
    return {"ok": True}
```

`username` を知っているだけで登録情報を削除できます。リクエスト中のパスコードも検証されません。

#### 修正案

- 有効なセッショントークンを必須にする
- セッションのユーザーと削除対象ユーザーが一致することを確認する
- 高リスク操作としてパスコードの再認証を要求する
- 成功時に対象ユーザーの全セッションを失効させる
- 削除専用のリクエストモデルを使用する

### 2. 並列リクエストで失敗回数を過少計上できる

- **深刻度**: 高
- **成立性**: 実際に再現可能
- **該当**: `server/app/store.py` — `authenticate()`、`_register_failure()`

失敗回数の読み取りと更新が別々のクリティカルセクションです。複数リクエストが同時に `fail_count = 0` を読むと、すべてが最終的に `1` を書く可能性があります。

```text
Request A: fail_count = 0 を読む
Request B: fail_count = 0 を読む
Request A: 1 を書く
Request B: 1 を書く
```

`threading.Lock` は同一プロセス内でしか有効ではないため、マルチワーカー構成ではプロセス間競合も防止できません。

#### 修正案

DB側で条件付きのアトミック更新を実行します。

```sql
BEGIN IMMEDIATE;

UPDATE credentials
SET
    fail_count = fail_count + 1,
    locked_until = CASE
        WHEN fail_count + 1 >= :max_fails THEN :locked_until
        ELSE locked_until
    END
WHERE username = :username;

COMMIT;
```

複数サーバーで運用する場合は、Redisなどを利用した集中型レート制限も必要です。

### 3. 成功と失敗の競合で状態が不整合になる

- **深刻度**: 中
- **成立性**: 実際に再現可能
- **該当**: `server/app/store.py` — `_reset_fails()`、`_register_failure()`

正しい認証と誤った認証が並行すると、古い失敗回数の書き戻し、失敗記録の消失、ロック直後の認証成功などが発生し得ます。認証結果の検証と状態遷移を、ユーザー単位で整合性のあるトランザクションにする必要があります。

### 4. 強度推定を通過する低エントロピー配置が存在する

- **深刻度**: 高
- **成立性**: 実際に再現可能
- **該当**: `server/app/passcode.py` — `estimate_bits()`、`assert_enrollable()`

次のように3種類だけを繰り返す配置が審査を通過します。

```python
[
    [0, 1],
    [4, 5],
    [8, 9],
    [0, 1],
    [4, 5],
    [8, 9],
]
```

実装上の推定値は次の通りです。

```text
distinct_patterns = 3
diversity = 3 / 6 = 0.5
corner_ratio = 0
estimated_bits = 41.44 - (1 - 0.5) × 22
               ≈ 30.44 bit
```

一方、「各面を3種類から選ぶ」という生成規則なら候補空間は最大でも次の大きさです。

```text
3^6 = 729
log2(729) ≈ 9.51 bit
```

単一の完成済みパスコードから、その人が用いた確率分布やエントロピーを推定することはできません。

#### 修正案

- サーバーが暗号学的乱数でパスコードを生成する
- 現行ロジックは「規則検査」または `pattern_score` と表現する
- `estimated_bits` や30 bitという暗号学的保証を表示しない
- 高い保証が必要ならWebAuthnなどと組み合わせる

### 5. 大きなJSON入力によるメモリ・CPU DoS

- **深刻度**: 中
- **成立性**: 条件付きで再現可能
- **該当**: `server/app/main.py` — `PasscodeBody`

`parse()` が要素数を検査する前に、WebサーバーとJSONパーサーが本文全体を読み込みます。巨大な配列や深いJSONによりメモリとCPUを消費させられます。

#### 修正案

- リバースプロキシまたはASGIミドルウェアで本文サイズを制限する
- Pydanticモデルにも外側6要素、内側2要素の制約を設定する
- エンドポイント単位・IP単位のレート制限を追加する
- 同時実行できるArgon2処理数を制限する

モデル側の制約だけではJSON解析前のDoSを防げないため、本文サイズ制限が必要です。

### 6. Argon2処理を利用した計算資源DoS

- **深刻度**: 中
- **成立性**: 実際に再現可能
- **該当**: `server/app/store.py` — `_dummy_verify()`、`authenticate()`

存在しないユーザーに対しても、リクエストごとに64 MiBのArgon2id処理を実行します。列挙対策としては合理性がありますが、無制限に並列実行されるとサーバーのメモリとCPUを枯渇させられます。

#### 修正案

- IP、アカウント、デバイスなど複数軸でレート制限する
- Argon2処理の同時実行数を制限する
- 負荷時にキューイングまたは早期拒否する
- ロックアウトだけに依存せず、遅延やリスクベース制御を併用する

### 7. セッション管理が本番運用に不足している

- **深刻度**: 中
- **成立性**: 設計上の問題
- **該当**: `server/app/main.py` — `_sessions`

```python
_sessions: dict[str, str] = {}
```

不足している要素は次の通りです。

- 有効期限とアイドルタイムアウト
- 明示的なログアウト
- 資格情報の削除・再登録時の失効
- プロセス間共有
- セッション数の上限
- セッショントークンを検証する認可処理

マルチワーカー構成では、認証を処理したワーカー以外からセッションが見えません。RedisまたはDBへ、トークンのハッシュ、ユーザー、有効期限、最終利用時刻、失効時刻などを保存する必要があります。

### 8. ユーザーの存在を列挙できる

- **深刻度**: 中
- **成立性**: 実際に再現可能
- **該当**: `server/app/main.py` — `status()`

```python
@app.get("/api/status/{username}")
def status(username: str):
    return {"enrolled": store.exists(username)}
```

このAPIは登録済みユーザーを直接公開します。また、ロック済みユーザーはArgon2検証を行わず即時応答するため、内容と応答時間からロック状態も識別できます。

### 9. 固定ロックアウトを第三者が悪用できる

- **深刻度**: 中
- **成立性**: 実際に再現可能
- **該当**: `server/app/store.py` — `MAX_FAILS`、`LOCK_SECONDS`

攻撃者は既知のユーザー名に5回失敗するだけで、そのユーザーを15分間ロックできます。繰り返せば継続的なサービス拒否が可能です。

#### 修正案

- アカウント単位だけでなくIP・デバイス単位でも制御する
- CAPTCHAや追加認証を段階的に要求する
- 指数バックオフを検討する
- ユーザーへロック通知を送る
- 安全な自己回復経路を用意する
- ロックアウトを監視・記録する

## C1–C7の判定

| Claim | 判定 | 理由 |
|---|---|---|
| C1: `120^6 ≈ 2.99兆 ≈ 41.44 bit` | **条件付きで妥当** | 数学的計算は正しい。ただし各面の120候補が独立かつ一様に選択される場合の理論値であり、人間が選ぶパスコードの実効エントロピーではない。 |
| C2: オンライン全探索は約1700万年 | **要修正** | 5回/900秒が完全に機能する場合の最悪時間。平均探索時間は約850万年。現実装では並列競合により試行制限を回避できる。 |
| C3: SHA-256なら約2.5分 | **要修正** | `K / 20 GH/s ≈ 149秒` は最悪時間として正しい。平均は約74.6秒。ソルト付きハッシュではターゲットごとに探索が必要。 |
| C4: Argon2idなら1 GPUで47年、1000 GPUで17日 | **要修正** | 2,000 H/sという仮定下の算術は正しいが、その速度が提示パラメータで成立する根拠が不足。平均探索時間は表記値の半分。 |
| C5: DB管理なのでリロードで回避不能 | **誤り** | ページリロードでは消えないが、並列リクエストとマルチワーカー環境で失敗回数を過少計上できる。 |
| C6: 強度判定で弱い配置を防止できる | **誤り** | `estimate_bits()` をすり抜ける約9.5 bit相当の規則的な生成例がある。 |
| C7: ユーザーの存在は秘匿される | **誤り** | `/api/status/{username}` が存在を直接公開し、ロック状態も応答内容・時間から識別できる。 |

## 数値の修正版

### 理論鍵空間

```text
K = C(16, 2)^6
  = 120^6
  = 2,985,984,000,000

log2(K) ≈ 41.44 bit
```

### オンライン試行

```text
rate = 5 / 900 ≈ 0.005556 attempts/second

最悪時間 ≈ 17.0 million years
平均時間 ≈ 8.52 million years
```

### SHA-256を20 GH/sと仮定

```text
最悪時間 ≈ 149.3 seconds
平均時間 ≈ 74.6 seconds
```

### Argon2idを2,000 H/s/GPUと仮定

| 攻撃規模 | 最悪時間 | 平均時間 |
|---|---:|---:|
| 1 GPU | 約47.3年 | 約23.7年 |
| 100 GPU | 約172.8日 | 約86.4日 |
| 1,000 GPU | 約17.3日 | 約8.64日 |

この表は、1 GPUあたり2,000 H/sが実際に達成できると仮定した計算です。GPU、実装、Argon2のバージョン、`m/t/p`、同時ハッシュ数、電力制限などを揃えた実測なしに一般化はできません。

## 推奨修正優先順位

1. `/api/forget` に認証・再認証・セッション失効を追加する
2. 失敗回数更新をDBトランザクションによるアトミック操作へ変更する
3. `estimate_bits()` をセキュリティ保証として使用しない
4. リクエストサイズとArgon2同時実行数を制限する
5. セッションを永続ストアへ移し、有効期限と失効処理を追加する
6. `/api/status` を削除または認証必須にする
7. 固定ロックアウトにIP・デバイス制御、段階的遅延、監視を追加する
8. 競合、巨大入力、マルチワーカー、セッション失効のテストを追加する

---

## 総合判定

**現状のまま本番認証へ使用するのは非推奨です。**
